# Сборка Java-плагинов для Purpurbedrock 26.2

Эта инструкция предназначена для разработчика VAC или другого Java-плагина. Она описывает сборку на основе текущего проекта, а не сборку самого VAC: команды и зависимости VAC нужно брать из его собственных исходников. Плагин и ядро — разные JAR-файлы.

## Окружение

- Целевая версия сервера и API: **26.2**, не 26.3.
- В сборке проекта используется **Java 25**. Gradle Wrapper проекта закреплён на **9.4.1**.
- Для первоначального получения Gradle, исходников и зависимостей во время сборки может потребоваться сеть. Это не означает, что сервер или плагин должны скачивать их при каждом запуске.
- В CI см. `.github/workflows/build.yml`: сначала подготавливается встроенный серверный протокол, затем применяются патчи ядра и собирается Paperclip JAR, API публикуется в локальный Maven, после чего отдельно собирается пример плагина NPC.

## Подготовка API

Из корня исходников ядра при наличии Java 25 выполните:

```bash
./gradlew applyAllPatches
./gradlew :purpur-api:publishToMavenLocal
```

В Windows вместо `./gradlew` используется `gradlew.bat`. Первая команда и публикация API могут требовать загрузки зависимостей; работа без сети заранее не гарантирована. Публикация кладёт API в локальный Maven (`~/.m2/repository`). Версию нужно проверить по фактически созданной папке `org/purpurmc/purpur/purpur-api`; в проекте версия по умолчанию — `26.2-R0.1-SNAPSHOT`.

Для последующих сборок отдельного плагина каждый раз пересобирать серверное ядро не требуется, если подходящий API уже опубликован и исходники API не менялись. Не компилируйте серверный исполняемый Paperclip JAR как замену API.

## Пример Gradle для отдельного плагина

Это пример зависимости, а не предложение заменить существующую систему сборки VAC. Сохраните его настоящие настройки, тесты и зависимости:

```kotlin
plugins { java }

java { toolchain.languageVersion.set(JavaLanguageVersion.of(25)) }

repositories {
    mavenLocal()
    maven("https://repo.purpurmc.org/snapshots")
    maven("https://repo.papermc.io/repository/maven-public/")
    mavenCentral()
}

dependencies {
    compileOnly("org.purpurmc.purpur:purpur-api:26.2-R0.1-SNAPSHOT")
}

tasks.withType<JavaCompile> {
    options.encoding = "UTF-8"
    options.release.set(25)
}
```

Если проект использует Maven, применяйте его существующий `pom.xml` и соответствующую зависимость API со scope `provided`. Если VAC требует дополнительные библиотеки или плагины, определите их по исходникам VAC и укажите честно: API Purpur сам по себе эти зависимости не заменяет. Не включайте API сервера в итоговый JAR плагина.

В качестве реального примера Gradle-модуля в этом проекте см. `purpurbedrock-npc/build.gradle.kts`. CI собирает этот модуль командой:

```bash
gradle -p purpurbedrock-npc build -PpurpurVersion=26.2-R0.1-SNAPSHOT --no-daemon
```

Это команда для примера NPC, а **не** проверенная команда сборки VAC. Для VAC используйте Gradle, Maven или другие инструкции, действительно имеющиеся в его исходниках.

## Установка и совместимость

У Bukkit/Paper-плагина должны быть корректные `plugin.yml`, главный класс, команды, права и зависимости согласно его исходникам; пример API-версии в этом проекте — `api-version: "26.2"`. Собранный JAR плагина устанавливается в `plugins/`; JAR ядра остаётся в корне сервера. Сохраните существующие настройки и команду запуска хостинга, не требуйте JVM-флаги. Используйте полный перезапуск, а не `/reload`.

Bedrock-клиенты представлены плагинам через Bukkit/Paper. При этом внутренние классы сервера не являются частью стабильного `purpur-api`. Например, `BedrockPlaceholderHook` находится в модуле сервера; существование метода в исходниках не означает, что его можно импортировать через `compileOnly` только с API. Если VAC использует внутренний мост, проверяйте доступность на нужной версии и возвращайте явное состояние «неизвестно» при отсутствии данных; не объявляйте успешной сборку, которую не запускали.

Сначала проверяйте VAC отдельно от других античитов на тестовом сервере: включение, команды, совместимость с ядром, настройки и отключение. Затем проверяйте реальные клиенты, сетевые задержки, PvP, мобов, копья, телепортации, меню и плагины. Компиляция или синтетический тест не доказывают отсутствие ложных срабатываний.

В проекте больше не собирается отдельный PurpurBedrockAC. Если его JAR уже находится на рабочем сервере, удаление модуля из исходников не удаляет этот файл автоматически: при остановленном сервере владелец должен отдельно убрать его из `plugins/`, сохранив резервную копию. Его Anti-ESP при этом перестанет работать; встроенный Anti-Xray ядра — отдельная функция.
