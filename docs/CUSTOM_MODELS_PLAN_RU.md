# Кастомные модели Bedrock: план и границы проверки

Цель: отдельный внешний вид для кастомных предметов, блоков и мобов без изменения обычных ванильных. Пока поддержка **не реализована целиком**, клиенты и реальные пакеты пользователя не проверены.

## Предметы

В закреплённом исходнике протокольного слоя уже есть выбор пользовательской модели по Java `item_model` и условиям маппинга. Условие по номеру `custom_model_data` также поддерживается отдельными предикатами (нельзя считать, что выбор всегда идёт исключительно по номеру или исключительно по имени). Сам по себе PDC не означает наличие подходящего отображаемого компонента; некоторые описанные плагины могут требовать доработок или адаптера.

Тестовая конфигурация `purpurbedrock-completions/tests/bedrock/fixture-sphere-mapping.json` повторяет предоставленный пример сферы. В изолированной CI-среде тестовый плагин выдаёт бумагу с `voidspheres:sphere1`, обычную бумагу и бумагу с другим `item_model`. Два синтетических клиента проверяют сетевые ID предмета в руке: соответствие даёт отдельный ID, два остальных случая — ванильную бумагу. Тест не содержит пользовательский ресурспак, не проверяет иконку, 3D, левую руку, GUI или клиентскую визуализацию. Никакие тестовые файлы не должны копироваться на рабочий сервер.

## Мобы

В закреплённом исходнике имеются события регистрации кастомных Bedrock entity и выбора определения при спавне по UUID. Однако отдельный идентификатор сам по себе не связывает его с конкретной сущностью на сервере. NBT-тег `pistoletov` не следует считать автоматически доступным в сетевом событии спавна: нужно создать потокобезопасный серверный источник соответствия UUID → модель, определить порядок регистрации/появления, загрузку сохранённых сущностей, изменения тегов, удаление, переключение миров и клиентов. Без этого ванильного зомби-коня нельзя надёжно отличить от кастомного.

Текущий, по описанию, ресурспак с `minecraft:zombie_horse` переопределяет весь ванильный тип. Для отдельной модели потребуется совместимая копия пакета с новым идентификатором и проверка анимаций, звуков, взаимодействия и отображения одновременно с обычным мобом. Файлы пакета не получены, проверить их нельзя.

## Блоки

Одного идентификатора недостаточно для замены конкретного установленного TNT: нужен достоверный тип по координатам из плагина, переживающий перезапуск и изменения мира. Маппинг по обычному состоянию TNT влияет на все блоки этого состояния. Отдельно проверять полные чанки, инкрементальные изменения, повторную загрузку, взрыв, слом, поршни, конкурирующие плагины, отключение клиента и обратное преобразование взаимодействий. Согласно предоставленному описанию HyperTNT сейчас теряет тип при перезапуске; фактический код и плагин не предоставлены.

## Ресурспаки

Сам сервер не может показать неизвестную клиенту текстуру без совместимого Bedrock-ресурспака. Не включать принудительную загрузку и не отключать уже действующий переключатель голов вслепую. Проверить совместимость нескольких паков и приоритеты, `manifest.json` UUID и версии, отсутствие переопределений `minecraft:*`, ситуацию отказа игрока и сохранение доступности сервера. Java-паки автоматически не превращаются в Bedrock-паки.

Не утверждать полную совместимость с произвольными плагинами/пакетами, пока нет реальных файлов, сценариев и клиентских тестов. Требуются сами исходники или архивы примеров (тестовая копия, без секретов): VoidTalismans и sphere mapping/pack; HyperTNT и конфиги; PistoletovPack. Предыдущий запрос пользователя: JAR пока не выдавать.
